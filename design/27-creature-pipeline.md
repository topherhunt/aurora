# §27 -- the creature pipeline

Wildlife and people, made from a sentence. One bench, `/gen-creature`, runs the whole chain: a candidate image, a mesh and texture generated from it, a skeleton, and animation clips -- each stage previewed before the next is paid for.

This is the first pipeline in the tree that **spends real money per click**, and that fact shapes every design decision below far more than the rendering does.

## Why a vendor at all

The tree already has two home-grown asset pipelines and both stay:

- `tools/characters/` -- chromakey a generated sheet, loft a mesh from the silhouette, rig, animate. Good for humanoids seen at village distance, and free per asset after the image.
- `tools/fauna/` -- the same idea for fish, where a lofted profile IS the animal.

Both work because their subjects are approximately extrusions of a silhouette. A fox is not. The loft has no answer for four legs that occlude each other, for antlers, or for a muzzle that is a different width than the skull. Rather than grow the loft into a general reconstruction engine, this pipeline hands that one job -- silhouette to volume -- to a vendor and keeps everything else local.

## Why Tripo and not Meshy

Meshy was researched first and rejected on one hard fact: **its rigging and animation API is biped-only.** There is no `rig_type` parameter, no quadruped entries in the API changelog through 2026-08-28, and every animation preview in its library is served under `biped/`. Its webapp guide claims "humanoid and quadruped characters", which contradicts its own API reference; the API is the thing being integrated, so the API wins. A pipeline that cannot rig a fox does not solve the problem that motivated it.

Tripo exposes seven skeleton families -- `biped`, `quadruped`, `hexapod`, `octopod`, `avian`, `serpentine`, `aquatic` -- which covers the whole intended roster.

**Tripo's animation library is nevertheless lopsided, and on a quadruped it is not merely thin but broken.** Bipeds get eleven presets on the v2.5 rig model; quadruped, hexapod and octopod get a single `walk` each, serpentine and aquatic a single `march`, and **avian gets none at all**. That one quadruped walk drives 7 of 36 bones and drags the fox's front paws through the floor -- Stage 5 has the measurement. So Tripo is used for the mesh and the *skeleton*, and **every clip is solved locally from the rig's own geometry**.

`PRESETS` in `tools/creatures/tripo.mjs` is the honest record of that coverage, including the empty `avian` array. `scripts/check-creatures.mjs` asserts the biped/quadruped asymmetry rather than papering over it, so the day it changes, the gate says so.

## The small texture is the gate, not the polycount

This is the load-bearing idea of the whole section.

**No generated asset enters the world with a colour map wider than 512px**, and the creatures that are a few pixels tall in the world -- butterflies, frogs, fish and crabs -- ship at 128px. `TEX_PX_MAX` and `TEX_PX_SMALL` in `tools/creatures/creature-roster.mjs` are the two numbers; a roster entry's `texPx` is the designation, absent means the cap, and `shipTexPx()` is the one place a shipper or the bench reads it from, throwing on anything over the cap. Tripo's 2048px originals stay in the work dir untouched, so moving a creature between the two sizes is one roster edit and a re-ship, never a regeneration. Triangle budget is a solved problem -- `face_limit` handles it, and `src/budget.js` says what the number has to be. The unsolved problem is that **a mesh's UV layout decides whether its texture survives being 128 pixels wide**, and nothing about the triangle count tells you that.

A high-fidelity model that is decimated down to budget gets its UVs re-solved after the fact, and an auto-unwrap of a decimated surface produces a scatter of many small islands. At 128px each island is a handful of texels; the smallest ones round away to nothing, and bilinear filtering bleeds neighbouring islands across every seam because there is no room left for a gutter. The full-size texture looks fine. The shipped one is mush.

**P1 Smart Mesh (`P1-20260311`) is the default for this reason.** It generates native quad topology with coherent edge flow rather than decimating a dense surface, so the unwrap yields fewer and larger islands, and those survive the downrez. It is also all-inclusive on price where H3 stacks surcharges, which makes the default the cheap option too.

The bench is built around checking this and nothing else is as important: `#texRow` draws the same texture into a 512px and a 128px canvas side by side, `image-rendering: pixelated` so the browser's smoothing does not flatter it. **Judge a candidate on the panel it ships at** -- the preview mesh wears the creature's designated size by default and never the 2048 source, because a creature evaluated under a 2k texture is a creature evaluated as it will never ship. Clicking either panel puts that size on the model, so the comparison is one click rather than a rebuild. `rotate light` turns a drag into swinging the sun instead of the camera, so the light sweeps across a still creature. H3 (`v3.1-20260211`) stays selectable for the case where a creature genuinely needs the fidelity and someone has looked at both panels and decided.

**Tripo's PBR maps are stored and not used.** `pbr` stays on because P1 charges nothing for it, so every pick's work dir holds the tangent-space normal map and the metallic/roughness map beside the colour at 2048; none of it ships and the bench drops all three on load (`matte()` in `gen-creature-main.js`), so the preview is the colour map on a fully matte material, like the world. The decision: per-region shininess from Tripo's roughness map was too inaccurate to trust on people or animals, and the normal map, judged under a swinging light, does not add enough at 128 or 512 to be worth a channel. Both shippers (`tools/creatures/ship.mjs`, `tools/fauna/ship.mjs`) write one opaque WebP colour map through `tools/tripo-pack.mjs` with `metallicFactor: 0, roughnessFactor: 1`; the frog and crab keep their wet-look GGX glint (`glint()` in `src/v2/render/critters.js`) at a hand-set uniform roughness, `WET_ROUGHNESS` in `frogs.js` and `crabs.js`, in place of the map. The gates (`scripts/check-frogs.mjs`, `check-crabs.mjs`, `check-fish.mjs`) read the shipped WebP's header and refuse a map that is not the designated side.

## The stages

| # | stage | vendor | cost | writes |
|---|---|---|---|---|
| 1 | species | -- | free | (form state) |
| 2 | candidate image | OpenRouter, FLUX.2 Klein 4B | ~$0.015 | `candidates/<n>.png` |
| 3 | mesh + texture | Tripo image-to-model | $0.40--$0.55 | `meshes/<n>.glb\|.fbx` |
| 3b | LOD ladder + card cross | **ours** (`src/mesh/decimate.js`, `src/props/impostor.js`) | free | `meshes/<n>-lod<k>.glb` |
| 4a | rig-check | Tripo | **free** | -- |
| 4b | rig | Tripo | $0.25 | `rig.glb` |
| 5 | animations | **ours** (`tools/creatures/anim/`) | free | `rig-map.json`, `anim-<clip>.glb` |
| 5b | animations | Tripo retarget -- bipeds only, in practice | $0.10 each | `anim-<preset>.glb` |

A quadruped is **75 credits, $0.75**: P1 mesh with texture, a rig, and a clip library that costs nothing. Buying three retargets on top would make it 105, and `check-creatures.mjs` pins that arithmetic, so a change to any price or default that moves it fails the gate rather than surprising the next invoice.

### Stage 2: the image is not a character sheet

`tools/creatures/creature-prompt.mjs` is deliberately not `tools/characters/sheet-prompt.mjs` and must not drift toward it. Those images get chroma-keyed and measured; this one gets handed whole to a reconstruction model that paints a texture from it. Three consequences:

- **Neutral light-grey background, never `#FF00FF`.** A saturated key bleeds a magenta rim into the fur of the shipped texture. The gate asserts no prompt asks for a chroma key.
- **Flat shadowless light.** Any cast shadow or rim light bakes into base colour and then fights `src/lighting.js` forever. Not undoable downstream.
- **Three-quarter view, not orthographic front.** Reconstruction wants depth; the chromakey loft wanted a flat measurable profile.

The pose clause is selected by rig type, because **a limb tucked against the torso is the documented cause of a bad auto-rig** -- the solver cannot find a leg it cannot see. Each clause asks for limbs held clear of the body; the serpentine clause, having no limbs to separate, forbids the body coiling across itself instead, which is the same failure in a different shape.

### Stage 3: quad topology, and what the +5 credits buy

H3 charges 5 extra credits for `quad: true`. **P1 rejects the field outright** (code 1004) rather than charging nothing for it, because quads are what it generates and there is nothing to ask for. `createMeshTask` omits `quad` for P1 for that reason -- `REJECTS_QUAD` is the list. The server's own error text says quad is supported only by `P2-20260801`; that is wrong, `v3.1` and `v2.5` both accept it, and P1 is the sole refusal.

**glTF has no quad primitive.** Mode 4 is TRIANGLES and there is no other option, so whichever model produced it, `mesh.glb` arrives triangulated and no runtime anywhere in this repo will ever see a quad. Paying for quad mode does not buy a different file format. It buys a different *arrangement* of the triangles inside the same format: a quad-generated mesh is triangle pairs that were coplanar quads a moment earlier, laid out in edge loops that follow the form.

That arrangement is not cosmetic, and it matters for exactly one reason -- the one the previous section is about. Edge loops that follow the form unwrap into few large UV islands. Scattered triangles unwrap into many small ones. At 128px the second kind is mush.

`estimateQuadFraction()` in `src/mesh/decimate.js` measures what survived: it greedily pairs adjacent triangles whose face normals agree to within `cosTol` and reports the fraction claimed. It is a lower bound and it is ambiguous on flat regions -- on a plane every neighbour is coplanar, so a flat grid reads ~0.91 rather than 1.0 while genuinely-independent planar quads read exactly 1.0. As a comparator between two meshes of the same creature it is still the right instrument, and the bench prints it next to the island count where the comparison is easy.

**Every Tripo mesh is drawn with backface culling, in the benches and in the world.** Tripo writes `doubleSided: true` and GLTFLoader honours it, but a Tripo creature's thin parts -- fins above all -- are closed slabs whose two sheets sit 0--0.1 mm apart wearing different texture islands, so drawn double-sided they z-fight at every distance. The meshes are consistently wound (0--4 conflicting edges in ~750 on the fish), so culling removes exactly the far sheet from any viewpoint. `src/tripo-culling.js` is the one place that rule lives; every loader of Tripo output calls it, `check-creatures.mjs` asserts they import it, and a world placement that needs double-sided has to say why at its call site. Welding near-coincident vertices does not help: half of a Tripo mesh's vertices are UV-seam splits at the exact same position, and the two sheets' triangulations do not line up, so no weld threshold merges them.

**Practically: pay it on H3, or use P1 and do not think about it.** P1 is the default and its price is all-inclusive, so the surcharge only ever arises when someone has deliberately chosen H3 for fidelity -- and having made that choice, refusing the 5 credits gives up the property that made H3 worth choosing. Five credits is $0.05 against a $1.05 creature.

### Stage 3b: the LOD ladder is ours

Tripo will also sell retopology. Buying it would put the one step that can be iterated for free behind a per-attempt charge, so `src/mesh/decimate.js` does it instead: quadric error metric, half-edge collapse, plain arrays in and out, no dependency on three so the same code runs in the bench tab and under `scripts/check-decimate.mjs` in node.

**The one rule: no vertex attribute is ever interpolated or invented.** Collapses are half-edge, so the surviving vertex stays exactly where it was and every UV and normal in the output is one the input already had; only the fit pass below moves positions, and it moves nothing else. The gate asserts it directly -- zero foreign UVs -- because a decimator that computes new texture coordinates is one that can put a corner in the wrong island, and that is the 128px failure arriving by a different road.

**That rule is also what lets a RIGGED mesh have a ladder for free.** Every output vertex IS one of the input's, and `sourceVertex` says which, so `tools/creatures/skin-ladder.mjs` carries `JOINTS_0` and `WEIGHTS_0` down the ladder by lookup -- exact, not a nearest-vertex guess -- and `decimateLadder` composes the map back to the ORIGINAL so a rung three down still indexes the mesh that was rigged. Nothing is re-rigged: a skeleton is a joint tree and a stack of inverse bind matrices, a clip is tracks naming joints, and neither mentions a vertex. So a shipped creature is **N meshes, ONE skin, ONE set of clips**, every tier node carrying `skin: 0`, and the file grows by the rungs' vertices and nothing else. `skinnedLadder` refuses a rig whose weights do not sum to one rather than renormalising the breakage into every tier. `check-decimate.mjs` gates the carry by looking each rung's vertices up in the original by UV -- the one attribute provably untouched -- and comparing the skin bit for bit.

The only pinned point is one where two open rims meet -- three or more open edges at a point. **A rim vertex is not pinned, a UV seam vertex is not pinned, and neither is a point on an edge three or more faces share.** A point with open edges collapses along one of them and nowhere else: `u -> v` is allowed when u and v share exactly one live face, so the outline loses one chord and v takes over u's other open edge if it had one; a collapse across the sheet, which would pinch the outline or pull it inward, is refused. Interior points may still collapse onto a rim. A point's count of open edges can only fall under this rule -- a rim point that a neighbour folds into keeps two, the end of a glued sheet's side rim hands its one over -- so `decimate` reads the count off the live faces per candidate rather than off a flag, and the pinned class stays static. The rule came from the leafkin in three steps. Its leaf loincloth is an open shell, all rim, and with rims pinned its 21 faces sat at source density on every tier while the size term thinned everything around them -- 14 faces, 7.5% of the 10% tier's budget, on 1.8% of the surface. Along its rim it goes 21 -> 9 / 5 / 3 with its triangles tracking the body's size, and an open 10x10 sheet reaches eight triangles at its full extent with its rim still a simple rim (`scripts/check-decimate.mjs`, "an open sheet thins along its rim"). That alone left the front of the torso a fan of slivers: its leaves are glued to the body along their bases, 22 edges with three to five faces each and 27 points on them, and a pinned point is a *sink* -- every neighbour may fold into it, nothing ever leaves -- so those points carried 24-face fans in the source and 19-face fans at the 10% tier while the arms and horns paid for them. The link condition (below) already handles an edge with any number of faces, so those points are simply free; and the last step frees the two ends of each glued sheet's side rims, which have one open edge each. `evenness` is the receipt, in `analyzeMesh` and every tier's stats: the 5th and 95th percentile face area over the mean and the largest fan at any welded point. The leafkin's 10% tier went from p5 0.23 / p95 2.15 / max 3.5 x mean with a 15-face fan to 0.47 / 1.87 / 2.4 with an 11-face fan, one piece, and reads as a figure again; a ball with six strips glued on along one edge each reaches 160 / 80 / 40 triangles with no fan past eight, p5 at least 0.50 and no rim ever meeting another ("a leaf glued along one edge pins nothing"). The coarsest leafkin's silhouette IoU went 0.62 -> 0.78 -> 0.81 over the three steps; under `stretch` the closed creatures are unchanged to four decimals, the ones with open hems, fins, hoods and glued sheets gain (shepherd 0.83 -> 0.90, ironscale-bass 0.72 -> 0.84, grasshopper 0.51 -> 0.53, thief 0.89 -> 0.90), and the losses are the shore-crab's 52-triangle tier (0.64 -> 0.62) and the glimmerfin's 48 (0.82 -> 0.80).

A welded point on a seam carries several *wedges*, one corner per island meeting there. A collapse `u -> v` is legal when a consistent map from u's wedges to v's corners can be read off the faces that contain both u and v, and each rewritten corner takes its mapped one. Because the correspondence is sourced from shared faces, every rewritten corner moves along an edge of a triangle the atlas already had: islands shrink, and no triangle can jump to unrelated texture. Where no consistent map exists -- a junction where three or more islands meet, whose wedges the shared faces never all mention -- the collapse is refused. `seamCollapse: false` restores the pinned behaviour and exists so the gate can measure the difference between them.

three's `SimplifyModifier` was read and rejected. It carries a `uv` attribute through, but `computeEdgeCollapseCost` is `edgelength * curvature` with no attribute term at all, and its border-cost branch is commented out. On a textured mesh it will happily collapse across a seam.

**The atlas floor is the ceiling, and it is a measurement.** Preserving the atlas cannot take a mesh below roughly one triangle per UV island, however the algorithm is tuned. The bench reports that floor directly -- it runs one throwaway `decimate(mesh, 1, { uvMode: 'preserve' })` and prints where it stopped -- next to the island count, the pinned fraction and the unremovable-face floor, so a stalled tier is explained before it is run rather than after.

The first real Tripo mesh, a P1 red fox at a 4000 face limit, came back at **487 triangles in 112 UV islands**, with 240 of its 250 welded points on a seam. That is not the closed organic surface with a single unwrap the vendor is sold as: 33 islands are one triangle, 24 are two, 19 are three, so **76 of the 112 are three triangles or fewer**. Wedge collapses take it from 485 triangles (0.4% off) to 291 (40% off), zero foreign UVs, islands 112 -> 105. **291 is the fox's atlas floor**, and no target below it is reachable with the atlas intact.

**`uvMode` is the way past it.** `preserve` is the behaviour above. `stretch` collapses the same edges `preserve` refuses, but every surviving corner keeps the UV it already had while its position moves: the UV triangle is an input UV triangle verbatim, only the 3D face under it changed shape, so the island's texels stretch over the new face and the tier still wears the original texture. Reduction is then bounded by geometry alone, and the price is texture sliding by one edge length per collapse -- on a 128px atlas seen at LOD distance, invisible. `drop` gives the atlas up entirely; the output carries no `uv` attribute, because two corners of one output triangle can come from unrelated islands and a `uv` slot filled anyway would look usable. In its place each output vertex carries a `sampleUvs` entry, where that vertex sat in the *original* atlas, which the bench reads the source texture at and bakes into vertex colours. `stretch` and `drop` produce identical geometry (the roster probe agrees to four decimals), so `drop` buys nothing but the loss of the texture; it stays as the fallback for a mesh that arrives without one. `auto`, what the bench uses, runs `preserve` first and switches to `stretch` when preserving missed the target -- or reached it only by climbing far higher up the cost order than `stretch` had to. Each pass reports `stats.maxCost`, the dearest collapse it made, and `auto` keeps the atlas when that is within `AUTO_SLACK` (3x) of the `stretch` pass's; a shattered atlas leaves `preserve` so few legal edges that it reaches the target by taking the wrong ones, which on the leafkin's 50% tier ground the loincloth to one face while the body kept two thirds. Across the roster a sane atlas reaches the target at 1.1 to 2.3 times the stretch frontier, a shattered one at 27 to 155; nothing sits between 3.4 and 4. The mode that actually ran is in `stats.uvMode` and in the bench's tier table.

On the fox, `auto` at targets 244 / 122 / 49 returns **243 / 121 / 49**, every tier textured, zero foreign UVs. A sub-50-triangle fox exists.

**Detached pieces are deleted, not collapsed, and pillows fold.** The fen-dragon (1848 triangles, 775 islands) is 46 geometric pieces (`piecesOf`: faces joined by a manifold edge or by a point that is neither pinned nor rim): the body, loose four-face tetrahedra, and its crest, which is a comb of *pillows* -- two faces back to back on the same three points, chained along the ridge by shared vertices -- on a few percent of the surface between them. Under `preserve` the tetrahedra's points are all seam-locked; and a pillow's base edge has one vertex opposite it, not two, so the classic link condition (exactly two shared neighbours) made every pillow immortal, and 58 of the coarsest tier's 184 triangles were ridge scales the size of a texel. Two things fix it. The link condition now asks that the shared neighbours be exactly the vertices opposite the edge in the faces containing it -- two on a manifold edge, one on a pillow -- so a pillow's tip folds in and takes both faces with it (a collapse that would leave no face at all is the one refusal). And `dropIslands` (on by default) prices deleting a whole piece at `(area + feature weight) * (diagonal / 2)^2` -- the units of an edge collapse -- and removes the piece the moment a *legal* collapse that costs more is about to be made; the largest piece is never a candidate. The comparison is against a collapse that is really going to happen, not against whatever is left in the heap: the pieces used to sit in the heap beside the edges, and on the leafkin under `preserve` (1917 triangles, 722 islands, 40 pieces, its legs and hips a separate 523-face piece carrying 38% of the surface) the legal collapses ran out at 2.7e-3 with the target still 300 triangles off, so the loop took the remaining pieces in cost order and deleted the legs at 1.32 -- five hundred times the dearest collapse ever made -- then reported "reached target", which `auto` accepted, and every lower tier was cut from a legless mesh. A tier that cannot reach its target by collapsing now says so, `auto` falls through to `stretch`, and the leafkin keeps its legs on every rung (`scripts/check-decimate.mjs`, "a piece is deleted only when a collapse that costs more is about to happen"). With deletion off the 10% tier is 86 triangles of spines standing on a 98-triangle body -- a row of teeth with no dragon under it. With both, `auto` at 924 / 462 / 185 leaves 7, 2 and 1 pieces (17, 5 and 1 of them deleted whole, the rest folded away), the coarsest tier has 9 triangles under 0.05% of the surface instead of 58, and every one of its 184 triangles is on the body: a dragon with wings, tail, head and legs. `analyzeMesh` reports the piece count and how many faces sit off the main one; the bench prints those next to the island count and, per tier, pieces in, pieces left and how many went whole.

**Reaching fifty triangles is not the hard part; still being a fox at fifty is.** What kills the ears is not the quadric being wrong, it is the quadric being *area-weighted*: an ear carries about one percent of the surface, so every collapse inside it is priced at one percent of a collapse across the flank and the ears are gone long before the torso has given anything up. Small features are cheap in proportion to how small they are, which is the opposite of what a silhouette wants. The second cause is that a plane quadric is blind along its own plane, which is exactly the direction a thin spike runs -- sliding an ear tip down to its base barely leaves any of the ear's own planes.

One term fixes both. Each point gets a *point* quadric, `w * |x - p|^2` in the same 10-float form, so it adds into the plane quadric and rides through every collapse; its weight is `featureWeight * importance * meanMass`, where `meanMass` is one point's share of the whole surface and so does **not** scale with the point's own area. Every point then resists dragging by the same absolute amount and `importance` decides how much it cares. `importance` is `turn + extreme`: `turn = 1 - |sum of area-weighted face normals| / area` is exactly zero on a flat patch of any size and near one both at an ear tip, where the normals fan, and in the notch *between* the ears, where they oppose -- lopping the ears off and welding the gap shut are the same failure seen twice. `extreme` is one for any point that is furthest along one of 64 Fibonacci-sphere directions, which is the definition of a silhouette point: nose, ear tips, toes, tail, the ridge of the back, nothing mid-flank. Global extrema, not local ones -- marking every point that beats its graph neighbours dilutes the signal to nothing (coarsest-tier IoU 0.770 against 0.790, maxDev 181mm against 153mm). The term only reorders collapses; it moves no position.

`scripts/probe-decimate-profile.mjs` is the measurement: it rasterises the source and each tier orthographically over 32 views (16 azimuths x elevations 0 and 25 degrees) at a **fixed frame**, so a shrunken silhouette cannot be rescaled back to full size and scored perfect. It reports IoU and **maxDev**, the worst symmetric one-sided gap in millimetres on a creature normalised to one metre tall -- symmetric, so a lopped ear and a filled notch both register. Over the whole creature roster (19 meshes, the bench's own 50/25/10% ladder, `stretch` mode with piece deletion on), the coarsest tier goes from **IoU 0.810 / maxDev 170mm at weight 0 to 0.828 / 109mm at weight 1**; across all tiers, 0.894 / 110mm to 0.907 / 64mm. The weight curve is a broad plateau from about 0.5 to 1.5 and `FEATURE_WEIGHT = 1` sits in the middle of it, so the figure is not load-bearing; 32 to 256 directions all land inside each other's noise. The term has a cost the silhouette score does not see: on the dragon at 184 triangles it spends the budget on claws, wingtips and jaw at the torso's expense, and at weight 0 the torso is rounder but the head flattens, the claws go and the worst silhouette gap grows from 106mm to 189mm. `preserve` mode improves too, but its numbers are not comparable -- it frequently stalls well above the target, which flatters any silhouette score.

Visually, on the fox at 46 triangles: with the term off the ear region is entirely missing and the front legs are largely gone; with it on the ears are there and the legs are solid. **The notch between the ears still fills in.** A saddle is neither a local maximum nor a minimum in any direction, so the extremal test cannot see it and only `turn` weights it -- and at 46 triangles there may be no vertex left to hold it open. `check-decimate.mjs` gates the mechanism on a fixture whose answer is known by construction: a coarse ball with two finely-tessellated cone ears grafted in, decimated to 40 triangles, must still reach both ear tips -- and must lose them at `featureWeight: 0`, at the same triangle count, so the check names what it is guarding.

**The plane quadric also cannot see triangle size or shape.** It prices every collapse across a flat patch at zero, whatever the triangle's size, so on a Tripo creature the big regular triangles of the back go as readily as the tiny ones on the snout, and it says nothing about the triangles a collapse leaves, so the back ends up a tangle of 3:1 and 4:1 slivers under a stretched texture while the snout and paws stay dense. Two more terms, both knobs in the bench's LOD box: a **size** term, `sizeWeight * meanMass` as a point quadric on every point, flat or not, which accumulates through collapses so the price of moving a vertex grows with how much surface has already folded into it and the cheapest collapse is always in the region coarsened least; and a **shape** term that multiplies the surface error by `(quality before / quality after) ^ shapeWeight` of the worst triangle the collapse reshapes, mean-ratio quality, relative rather than absolute because the eared ball's ears are slivers by construction and an absolute penalty made fixing them the cheapest thing on the mesh. The feature term rides in its own quadric added outside the multiplier, so it stays absolute. Both terms compete with the feature term on the same fixture, since a feature *is* small triangles: from `sizeWeight` 0.25 up the size term outbids it, and at `shapeWeight` 2 the eared ball loses one tip at 40 triangles. The shipping defaults are `SIZE_WEIGHT` 10 and `SHAPE_WEIGHT` 1, chosen by eye on the bench, where the fox at the 25% tier is a regular lattice everywhere and reads far better than any smaller weight; the price is paid at the 10% tier, where the size term wins outright and the fox loses its ears and its legs become stubs, and the eared ball at 40 triangles reaches 0.81 / 0.90 of its tips instead of 1.00 / 1.00. Over the pinned 19-creature roster at the coarsest tier, measured with the fit pass off, the silhouette score says the same thing: both terms off gives IoU 0.831 / maxDev 111mm with mean quality 0.617, p90 aspect 8.6:1 and 46% of triangles worse than 3:1; `sizeWeight` 0.05 gives 0.824 / 126mm at quality 0.671, p90 6.5:1, 39%; the default 10 gives 0.727 / 181mm at quality 0.746, p90 4.9:1, 24.5%. The score measures the coarsest tier, which is where a distant creature is a few pixels tall and the lattice cannot be seen anyway; the gate only asks the defaults to reach three quarters of both ears.

**Half-edge collapse shaves volume, and the fit puts it back.** A coarse face is a chord strung between points that were on the surface, and on a convex body every chord lies inside it, so a coarse tier is the original with its volume shaved off, deeper the coarser the tier. The marsh frog at 64 triangles kept 62% of its volume and lost 12% of its height, most of it out of one side of the back -- a 135mm gouge, lopsided because on the smooth back the size term outbids the plane quadric and collapses are chosen by edge length, not by surface error. No collapse-order knob fixes it (`sizeWeight` 0 gets 81%; `flipTolerance`, `featureWeight` and `shapeWeight` do nothing), because the loss is in the placement, not the order. So `decimate` ends with a fit: every welded output point slides along its own normal to the least-squares fit of the source surface to the coarse one -- samples are the source's welded points and face centroids, area weighted, re-paired with the closest point on the coarse surface eight times with twenty bounded mean-residual steps each, residuals further than twice the median coarse edge ignored so a leg's samples do not pull on the belly above it. Least squares on a convex body sets vertices *outside* the surface and left alone the fit grows the bounding box by a quarter, so after every step a point outside the source and further from it than `FIT_OUT` (0.5% of the diagonal) is pulled back to that distance. Outside is decided by ray parity, not by the nearest vertex's normal: a point strung between two antler tines is a centimetre from the nearest tine and no normal test can tell it from a point on the tine, and with the normal test the stag's antler stub ballooned into a blob (IoU 0.484 against 0.542 unfitted; 0.584 with parity). The ladder fits every tier to the original, not to the tier above, so the fit undoes the shave rather than chasing it. On the frog at 64 triangles the fit takes volume from 62% to 93%, rms surface error from 72mm to 34mm and silhouette IoU from 0.723 to 0.879; over the 22-creature roster's coarsest tiers (`stretch`, the bench's 50/25/10% ladder) it goes from **IoU 0.706 / maxDev 270mm to 0.802 / 176mm**, all tiers from 0.833 / 167mm to 0.878 / 115mm, 21 creatures better and the birch spider flat; caps of 0 and 1% both score under 0.5%. The frog's ladder goes from 50ms to about a second. The one rule is intact -- corners keep their UVs, so the atlas triangle under a fitted face is an input triangle verbatim, as under `stretch`.

A regular grid was tried against it: sweep rings of eight points along the body's principal axis, each point the slab's extreme sample in that direction, then fit. At 10% it loses to decimate-and-fit on the frog (0.892 against 0.912), fox (0.746 against 0.803), stag, crab and goose, and beats it only on the shepherd (0.855 against 0.828), whose body is a tube along one axis; at 64 triangles, where the decimator stalls at 112 on the shepherd's pinned points, the sweep's 0.804 against 0.730 is the one clear win. Not promoted: a candidate for the bottom tier of humans only, and it needs its own texture mapping, since a sweep has no atlas.

A quad term was tried and removed: pairing each face with the one across its longest edge when they lie within 18 degrees, and multiplying the cost of any collapse that leaves half a quad standing. A half-edge collapse reshapes every face around the vertex it removes, so the quads next to a "diagonal" collapse are distorted rather than orphaned and the penalty never bites; re-pairing after each collapse did not change that. Measured on five creatures at every tier the surviving clear-cut-quad fraction was the same with the term at 0, 3 and 10, and it cost silhouette. Keeping quads as quads needs a quad operator -- diagonal collapse with edge rotations, or poly-chord removal -- not a price on a triangle collapse.

Welding harder does not help and eventually hurts. Decimating the fox's geometry to 49 triangles reaches it at every tolerance from the default (`1e-6` of the bounding diagonal) up to 0.5%; at 1% it overshoots to 43, and at 2% it *stalls at 101* with 42 points locked, because fusing across a gap makes non-manifold edges that then pin themselves. The blocker was never positional duplication. The bench exposes the tolerance as a percentage of the bounding diagonal anyway, defaulting to the hair-thin value.

H3 with `smart_low_poly` (+10 credits, H3-only -- Tripo rejects it on P1) is the other lever: it retopologises and re-unwraps rather than decimating what P1 emitted, so it should arrive with a coarser atlas and a higher floor to begin with. The bench has a checkbox for it next to the model selector.

This repo's own props hit the ceiling for two different reasons, neither of which is the fox's:

|---|---|---|---|---|
| `gen_oak_LOD0` | 494 | 2 | 88% | 28% |
| `tree_cracked_dead_LOD0` | 500 | 120 | 95% | 2% |

The oak is open surfaces -- leaf cards, an open trunk -- so almost every vertex is on an open rim, which was pinned when this was measured; a rim now collapses along itself. The dead tree is atlas-mapped with roughly an island per face. Both are already-baked Blender LODs, measured before seam collapses existed.

Tiers are decimated from the tier above rather than from the original, so tier 2's vertices are a subset of tier 1's before each tier's fit moves them, and swapping between them does not pop.

**A ladder belongs to the mesh candidate it was decimated from**, not to whichever candidate happens to be picked. The bench has a *selected* candidate as well as a picked one -- picking is what rigs and ships, selecting is what section 4 operates on -- so two candidates from the same image can have their ladders built and compared without committing to either. `saveLod` files each tier under the source candidate's stem and records its triangle count in `state.json`, which is how the table lists a saved ladder without opening every glb to count faces. Swapping between the source mesh and any of its tiers holds the camera where it was: a comparison whose viewpoint moves between the two frames is not one, and the eye reads the reframing as the change.

**The bottom rung the bench offers is not a mesh, and most creatures should not take it.** Below about fifty triangles the silhouette is the whole of what reads, and the cheapest honest way to draw a silhouette is to photograph it: `bakeCardCross` in `gen-creature-main.js` takes two orthographic captures -- one along -Z, one along -X -- and hangs them on two crossed quads. **Four triangles, two 128px textures**, which is the same asset shape `src/props/impostor.js` already ships for ferns and whose pure pixel helpers it reuses. Captured at `SUPERSAMPLE` and boxed down in JS rather than rendered straight at 128, because an alpha-tested cutout rendered at its final size has a binary one-texel edge that every mip afterwards guesses at; then `dilate` pushes colour into the transparent margin, because bilinear filtering at the silhouette blends *toward* unwritten texels and an unwritten texel is transparent black. The bake rig is impostor.js's, with `BAKE_ROCK_BOUNCE` for the ground term rather than the near-black canopy value -- a fox has no shaded interior, and baked against a canopy bounce its underside comes out a black wedge. The key light rides each capture's own azimuth so no left-right terminator is burned into a card that gets seen from both sides.

**In the world a card is the exception.** It is right for a creature seen far off in one fixed pose from one side -- the shore crab clinging to its boulder, drawn as `CRAB_VIEWS` in `src/v2/render/critters.js`, or the birch spider flat against its trunk, one quad photographed from above (`setCritterCard` takes one view or two) -- and wrong for anything that turns, hops or is walked around, where the two planes show their seam and the cutout's flatness from most angles. Those creatures (the frog, and expect most of the roster) are drawn as the mesh at every distance: the world ladder's four rungs (`critterTier`), pared harder at the bottom than the bench's 50/25/10% default so the last tier is a few dozen triangles, and then nothing at all past the last rung (29 m for the biggest frog, 10 for the smallest), where a creature is a handful of pixels and its absence is not missed. The pressure this puts on the decimator, not the card bake, is where a creature's far look is won or lost.

**The birch spider ships as one animated GLB, and the world draws it with no skeleton at all.** `tools/creatures/ship-spider.mjs` writes `public/creatures/birch-spider.glb`: the authored skeleton (`rig-spider.mjs`), four skinned tiers bound to it -- the rigged mesh and the 50%, 25% and 12.5% rungs `skin-ladder.mjs` decimates out of it, 480/240/120/60 triangles -- and the six clips as one animation each, plus the usual 128px WebP beside it. `src/v2/render/spiders.js` scatters groups of one to five on trunks (`Trees.trunksInto` hands over the LOD0 trunk's own ring profile with the instance's scale and yaw, so a spider is seated between the bark's corners and never off it; the trunk's wind lean is held to a floor by `WIND_PRESETS.tree.limb`, so the bark it sits on stays put while the boughs sway) and on boulders (`Rocks.rayAt`, a ray against the hull's own triangles; only faces above the ground and the water, with `WALL_M` of wall to climb, and a spider whose stone re-seats or goes is re-read or taken away), 0-3 m up and almost never on top of anything, crawling and pausing. Every spider is an instance of one of three InstancedMeshes: within 10 m the GLB's first two skinned tiers as plain instanced geometry, tier 0 on the ladder's first rung (`critterTier`) and tier 1 held out to 10 m rather than culled, and past 10 m one quad, the bind pose baked from above under the same matrix, edge-on against the bark. The coarser two shipped tiers are not drawn (they read as smears at spider size). THE LEGS ARE THE VERTEX SHADER: `setAsset` reads each tier's vertices against the skeleton's joints and weights and bakes onto the ones a `Leg*` bone owns their half of the alternating tetrapod and their depth down the leg (`aLeg`); a per-instance phase and amplitude (`aGait`) swing them fore and aft and lift them on the forward swing, the phase running one cycle a stride of the seat so the feet hold the bark, the amplitude easing to nothing at a pause. Her head close by pitches a paused spider nose-up about its seat instead of playing the alert clip. No mixer, no bone matrices, one program for the mesh tiers and three draw calls for the lot; a spider's matrix is composed only when it has moved, turned, re-seated or is rearing. `scripts/check-spiders.mjs` gates the shipped file's shape and the scatter on a synthetic wood.

**The three wandering quadrupeds ship the same way, and the world scatters them by area.** `tools/creatures/ship-quadruped.mjs` writes `moor-stag`, `red-fox` and `snow-hare` into `public/creatures/`: the rigged mesh (Tripo's for the fox and hare, `rig-stag.mjs`'s for the stag), four skinned rungs over that one skin (`skin-ladder.mjs` at 50%, 25% and 12.5%: stag 2032/1016/508/254, fox 474/236/118/58, hare 905/452/226/112), the whole `anim/clips/quadruped` library as one animation per clip, and one 512px WebP. **The shipper decimates what it is about to ship, in process**, never a ladder saved on the bench: Tripo's rigger may hand back a different mesh than the candidate that was rigged, and a ladder built from the bench's copy then belongs to a mesh the file does not contain. The work files are already nearly the shipped file (`anim-<clip>.glb` is a copy of the rig with one clip in it), so the shipper reads the first as the body and takes only the animations out of the rest. What it changes is the FRAME: the world wants a creature facing +X, feet on y = 0, middle over the origin, and the whole correction is premultiplied onto the ROOT JOINT -- its rest transform and every sample of the root's translation and rotation -- with the `Armature` folded into the same product and dropped. Not a vertex, an inverse bind matrix or a limb track moves, because premultiplying the root is exactly a change of the space the skeleton hangs in. The scene's `extras.quadruped` carries what the world needs to place it without opening a mesh: `sizeM`, the turned extents, the frame that was applied, the ground speed of each gait in the file's own units, so a puppet's feet do not skate at any size, and `legs` -- each leg's joint chain, hip to foot, by name, off the rig map -- for the foot IK below.

`src/v2/render/wildlife.js` scatters hares at one per 3000 m² and stags and foxes at half that rate over 32 m tiles within `RADIUS` (311 m) of her -- the card reach of a 4 m body plus half a tile's diagonal, so nothing this layer holds is ever waiting on its tile to appear -- rejecting water, slopes past 35 degrees, trunk footprints and anything within 10 m under the snow line, and tethers an animal to 24 m from where it was placed. An animal rolls a weighted activity -- graze (`eat-down`, a whole number of `eat-loop` chews, `eat-up`), stand, roam at a gait, dig, rest (`sit` or `lie`, each a whole round trip played once) -- and walks at exactly its clip's shipped gait speed times its scale. Past `FLEE_M` (6 m) it **takes no notice of her**; inside it a stag or hare startles, faces her and runs, unless she holds a carrot (wildlife.js header, WHAT SHE DOES TO THEM). The gate proves the first half by running the same world twice with her at two heights ON THE SAME RUNG -- 7 m and 8 m straight over a stag -- and comparing the traces frame for frame. Her distance does change one thing, how often the animal thinks (below), so a trace cannot be compared across rungs; there the gate promises the weaker true thing instead, walking her up every rung in turn and finding the animal still on its tether after fifteen seconds rather than over the horizon. A body turns at `TURN_RATE` and never faster: `aim` is where it wants to face and `heading` is where it faces, the gap closes at that rate, and a step is scaled by the cosine of the swing still owed, so a beast mid-turn slows and one turning back on itself pivots on the spot. No two are the same animal: each rolls its own size within `vary` (±25%) of the species' drawn length, which is the roster's `sizeM` times the species' `scale`, 1 for all three.

**A SKINNED BODY WEARS NO COLOUR OF ITS OWN, and that is a rendering limit rather than a taste.** An `InstancedMesh` varies its instances through an ATTRIBUTE -- `aHue` on the frogs, crabs and fish, `instanceColor` on the trees and rocks -- and the whole scatter stays one material, one program and one draw however many hues are in it. A puppet has no instances: the only place a per-animal value can sit is a UNIFORM, and a uniform belongs to a material, so twenty hues meant twenty materials. Three refreshes EVERY uniform of a material it did not just bind (`setProgram`, `refreshMaterial`), so each drawn animal cost a full uniform upload -- twice over, the WebGL renderer having no multiview and drawing each eye in turn (§15 holds the spike that would settle whether the Quest could offer one). Wildlife and snowmen therefore share ONE settled material a species (`makeSettledMaterial`) and keep a dissolve pair per puppet for the third of a second a fade lasts, so a settled herd is one material change a frame instead of one an animal; the cards agree, baked flat, so nothing changes colour as it swaps. The per-animal SIZE roll stays: a transform is free.

**Night settles them.** `dayness`, the world's one day scalar (1 at noon, 0 once the sun is well down), is handed to `update()` every frame, and `_pick` multiplies the weight of `rest` by `NIGHT_REST` at full dark on a ramp through the evening -- so a herd at midnight lies down about twice as often as the same herd at noon, and half the ramp is spent before the sun is even down, which is when a real herd starts settling. The butterflies take the same scalar and go further: below `NIGHT_DAY` (the sun on the horizon) a flight ends at the next perch it can find, no landed butterfly takes off again, and a meadow that rolls in the dark arrives already seated. A rest in the dark is re-rolled rather than left expired, so dawn does not launch the whole meadow on one frame.

**ONE LADDER, FOUR MESH RUNGS AND A CARD UNDER THEM, AND IT IS AN ARC THE BODY SUBTENDS -- the standard for everything that animates, stated in §5 and detailed here.** `src/v2/render/critters.js` holds the ladder every creature in the world walks, and a new creature or NPC takes its tiers from it rather than writing distances of its own: `lodReach(size, k) = distAt(size, LOD_DEG) * LOD_STEP ** k`, over `distAt(size, deg) = size / (2 tan(deg/2))`. Tier 0 holds until the body has shrunk to `LOD_DEG` (12.7 degrees) of arc, and each rung below it holds to half the arc of the one above, which is `LOD_STEP` (2) times as far -- so four mesh rungs draw a body out to an eighth of that arc, and the wildlife hangs a fifth rung under them, a spun card, carrying to twice that again before the cull (`CARD_RUNGS`, below). Arc and body-count are the same ladder, a body subtending 12.7 degrees at 4.5 of its own lengths away whatever it is, but degrees are the units the eye works in, so that is the dial. **Size is the body's LARGEST extent**, whichever axis it lies along: the wildlife hands `critterTier` `size * bulk` (the shipped mesh's longest side over its length, so a tall animal is not measured by its length), a snowman hands its height. `critterTier` carries `LOD_HYSTERESIS` (10%) pushed away from whichever rung the body is already on, so a body sitting on an edge does not flicker. The rungs come out at 10/20/40/80 m for a stag (2 m tall, 2.23 along its longest axis), which is where `LOD_DEG` came from -- a first swap she can walk up to and watch -- 6/13/25/50 for a fox, 2/4/9/18 for a hare, each with its card to twice the last of those. **The ladder does the culling now, not the tiles**: the furthest an animal can be and still be scattered is `RADIUS` plus half a tile's diagonal, 334 m, and the far end of the card roll across all three species is 200 m, so every animal in the world fades in on its card well inside the ground it stands on. **A swap is not verifiable by eye without instrumentation** -- halving the triangles of a smooth mesh barely moves its silhouette, which is the point of an LOD -- so two rows in the Quest panel exist to read it: `critter lod` gives drawn animals and their triangles rung by rung, and the `critter LOD tint` toggle flat-colours every creature but the butterflies by the tier it is drawing (green, yellow, orange, red, and blue for a card; a creature shipped as one mesh wears that tier's colour), which turns walking up to a stag into a measurement.

**Past the cull a creature is not simulated either, and its placement outlives it.** A tile's roll produces SPAWNS -- the home seat, the size and heading, and the spawn's own mesh cull, card reach and forget distance -- and a spawn is woken into a live animal (a SLOT: a wandered position, an activity queue, a puppet) only inside its CARD reach, the end of the whole ladder. Past that the animal freezes exactly where it stood: nothing walks, turns, probes the ground or picks an activity. One `critterTier` call decides both the rung it is drawn at and whether it is alive at all, so there is no band where the mind runs on something she cannot see. Where it had wandered to is remembered until she is `CULL_KEEP` (1.5x) past the card, and past that the slot goes back in the pool and the next waking stands it at home again.

**AND A FAR ANIMAL THINKS LESS OFTEN, by the rung it is drawn at.** An animal's frame is its GROUND WORK -- the seat test a body length ahead, the height under its feet, the normal it stands on -- and each of those walks every stone and every piece of deadwood in the world (`walk.js` `heightAt`). That, not the skinning, is what a herd costs: a mixer update is 3 microseconds and a dozen drawn animals are 0.05 ms of mixer against a frame budget of 16. So the ground work is bucketed by rung -- `PROBE_EVERY` (6/8/12/16/30 frames, staggered across the herd by slot id so no frame carries the whole herd) -- and an animal on its card reads the ground a fifth as often as one at her feet. **Between probes it rides the TANGENT PLANE the last probe measured** rather than holding the height it had: `y -= (nx dx + nz dz) / ny`, exact to first order, which is what makes a long stride cost nothing visible. The gate measures the float in the currency the ladder is already in and finds it never worth a quarter-degree of her view, and every probe seats the animal on the ground exactly again, so nothing accumulates. Dropping ANIMATION rate with distance was measured and rejected: the mixer is not where the money is. The home seat itself is a pure function of the seed and is never forgotten while the tile is loaded.

**THE LAST RUNG IS A CARD, AND NOTHING POPS.** An animal on a mesh rung is a pooled puppet -- one clone of the shipped skeleton under a mixer, every rung bound to that one clone. One rung further out it is an instance of its species' `InstancedMesh` instead: a single quad, spun about its own Y in the vertex shader to face her, carrying the animal's size in its matrix, photographed once off the idle-posed body when the GLB lands (`bakeCards`, one `side` view through `bakeCritterCard`). **Only at the bottom, and only for reach.** A card does not walk, and a creature standing still among creatures that are walking reads as broken -- so the rung is kept where the body is a dozen pixels tall and the stride it is not taking is under a pixel, from 1.6 degrees of arc to 0.8. What it buys is not triangles but PRESENCE: a herd she is walking toward dissolves in at 160 m rather than appearing at 80, and a hare at 36 rather than 18, which is the case that made it unbearable. The animal behind the card is unchanged -- still wandering, grazing, turning for home, just thinking a fifth as often -- so a field of cards is a field of animals that have moved by the time she is close enough to see them as meshes. Appearing, vanishing and every step between rungs, the card included, is a DISSOLVE over `LOD_FADE_S` (0.35 s): the two rungs read one screen-space hash of `gl_FragCoord` at the same pixel and compare it opposite ways round, so the masks are complementary rather than merely both dithered. **Timed, not banded** -- teleport locomotion crosses a whole band in one frame, so a fade driven by distance across a band edge would still pop. A settled puppet draws through a material with no `discard` in its shader at all, which is what keeps early-Z on the Quest's tiled GPU; only a fading one draws through the dissolve pair, for two draw calls for that third of a second. A puppet is not returned to its pool until it has faded out, and its slot keeps walking and animating it while it goes. **The card dissolves WITH the mesh, not after it**: the mesh's cut and the card's coverage are one number against one hash, so what she loses off the body she gains on the quad and the pixels are partitioned through the whole swap rather than doubled or dropped (`cardFade` positive while the card arrives, negative while it leaves, the sign being which half of the hash it keeps). A reversal mid-fade rewinds the fade already running rather than starting a second, on both halves at once. **A tile unload dissolves too, but it is no longer anybody's usual exit**: `RADIUS` is sized off the card of a 4 m body, so every card in this layer ends well inside the loaded ground and the ladder is what takes an animal away; a body still in sight when its tile goes keeps its puppet for one fade, standing where the animal was (`Wildlife.fading`). The one hard pop left is `place()`, the terrain rebuild, where the ground a body was standing on no longer exists. `scripts/check-wildlife.mjs` gates the shipped files' shape and the scatter on a synthetic moor of pond, crag, trunks and a ramp into the snow, the rungs and their hysteresis, the probe stride on every rung, the tangent-plane float in degrees of arc, the card's instance (its place, size and fade) and the two-way partition of the card dissolve, the frozen mind and the forgotten wandering, and counts the frames a teleport past the cull takes to dissolve.

**What that costs, measured in the live world** (headless Chrome against the dev server, her standing in open moor, 22 animals inside `RADIUS`): 12 of them were in sight and drawn, for 12 draw calls, 20,141 triangles and 372 bones across 12 skeletons -- 9 stags of 9 (a stag's reach was past `RADIUS` then), 2 foxes of 5, 1 hare of 8. Against the whole frame that is 12 calls of 66 and 20k triangles of 221k. **What the ladder changes is the triangles and nothing else.** Over 60 seeds of open ground (1972 animals, 32.9 inside `RADIUS` at a time) the ladder drew the same 20.2 animals a frame as one tier would, and the same 614 bones, for 10,532 triangles against 27,010 -- 61% off -- because 13.2 of the 20.2 sat on the bottom rung and only 1.7 on the top. That was taken on an older three-tier ladder: this one adds a fourth rung at an eighth of the triangles and culls a stag's mesh at 80 m, so both numbers fall and the saving grows, and the card rung and `PROBE_EVERY` came after it again -- the card adds instances and no skeletons, the bucketing cuts the ground work by roughly the stride. Not re-measured since. **A ladder buys triangles and draw distance and buys nothing at all on the skinning**, so the POSE CADENCE is a second lever laid over it: `skeleton.update` is deduped per frame but still runs once for every skeleton DRAWN, whichever rung it is drawn on, so `POSE_EVERY` (`puppet.js`, `[1, 1, 2, 4]` by rung) re-poses a bottom-rung body one frame in four -- no mixer, no bone composed, no bone texture built or uploaded; a pose is ~4 us of desktop CPU for a 31-bone stag, so the lever is worth under a millisecond at a crowd of twenty and is kept only as far as the held frames are not seen -- and banks the skipped dt to spend whole, so the clip plays at its own speed however coarsely it is sampled. The rig is DETACHED -- the bones hang under no scene node, `matrixAutoUpdate` off, composed and walked by hand on pose frames only -- so their world matrices are creature-space, the bone texture holds the pose alone, and the group's matrix places the body: the layers write it every frame, so a held puppet slides on smoothly in the pose it last took, and a held frame costs the group and its four tier meshes a multiply each and never touches a bone. (With the rig hung under the group the bone texture holds world matrices, a stale one draws the body frozen where it stood, and the animal crosses the ground in hops of its own cadence -- which was plainly visible in the headset.) **And every tier is frustum-culled**, on one explicit sphere over the rest bounds with half again for the pose: `projectObject` calls `objects.update` INSIDE the frustum branch, so a body behind her loses its bone-texture upload along with its draw, and an explicit sphere is what keeps `SkinnedMesh.computeBoundingSphere` -- which CPU-skins every vertex -- from ever being reached. `Wildlife.update` costs 0.257 ms a frame for all 22, of which the 12 mixers are 0.039; `skeleton.update` for all 12 is 0.012 more, paid inside the renderer. The butterflies are 43 instances in one draw call at 0.127 ms. **In XR the draw calls double and the skinning does not**: three r180 renders an `ArrayCamera` by looping `renderScene` per eye, so each puppet is submitted twice, but `skeleton.update` is deduped per frame on the skeleton, so the bone matrices and their ~2.3 KB texture upload apiece are paid once. The three dials, in the order to reach for them, are `LOD_DEG` (every rung and the cull move together with it -- a wider arc pulls the whole ladder in, and the crowd in sight goes as the cube of the reach), `PUPPETS` (20, sized off the Poisson tail of the expected crowd so a starved animal -- one in sight and undrawn -- is a ~0.1% event), and `DENSITY`.
**The abominable snowman is the first biped shipped, and the first creature that notices her.** `tools/creatures/ship-biped.mjs` writes `public/creatures/abominable-snowman.glb` through `ship-skinned.mjs`, the one shipper the biped, quadruped and wyvern files all call with their plan (`human` here), the gaits that carry the body forward (walk and run) and the key the world reads the extras under (`biped`): 1891/946/472/236 triangles over Tripo's 33-joint skin, the whole `anim/clips/human` library (17 clips), the frame on the root joint, and a 512px WebP. Its `rig-map.json` is hand-written: Tripo's biped rig has stub joints beside every forearm and toes 42 degrees off every world axis, so the derivation refuses it, and a map that names the chains outright is what the solver needs anyway. `src/v2/render/snowmen.js` scatters one per 40,000 m² on the same tiles and seat as the wildlife but ONLY above the snow line (wood or open alike), 2 to 6 m tall, and runs three states off her distance: **cower** (found crouched and flinching at nothing, facing wherever it was rolled), **watch** once she steps inside a 10 m half-disc AHEAD of it -- behind or beside it she can stand at arm's length unnoticed -- (turns to her at `TURN_RATE` and keeps her in front, beckoning and gesturing with the talk clips, staring between), and **follow** the moment she is 3 m further off than the closest she came -- walking inside 12 m and running past it, stopping 4 m short of her to watch again, skirting water, trunks and faces past `FOLLOW_SLOPE` (55 degrees -- steeper than she can climb, so a shelf she walked over never holds it back, where it is only ever LAID on ground under 35) by the wildlife's probe with a side it keeps for 4 s so a tarn is gone round one way, and crossing the snow line downhill after her without a tether. It stands on the world vertical whatever the ground does, as the wildlife does: a body is yawed about the world up and never tilted onto the ground's normal, since a stag or a biped on a hillside is upright. **What meets the hillside is the feet, and only when the body is still.** `puppet.js FootIK` is a two-bone solver over the shipped `legs`: a layer's one call a frame, `groundFeet`, reads the ground under each rest foot -- once when the body stops on a clip whose feet stay put (`PLANTED` in each layer: idle, alert and the graze for the wildlife, since a dig lifts a forefoot and a sit or lie folds; the stand, the cower and every gesture for the snowman, since a recoil steps a foot back; never a gait) and again on a probe frame once it has turned `REPLANT` (0.2 rad) on the spot -- and hands the puppet each foot's vertical offset in creature units. On a posed frame the solver adds that offset to the clip's own foot position, so an idle that shifts its weight still shifts it: the knee, chosen at rest as the interior joint furthest from hip and foot, closes or opens by the law of cosines about the axis the pose already bends it on, and the hip turns the leg onto the target; the root drops by the mean offset and further whenever a downhill leg would have to reach past its length, so a body across a slope sits lower and bends its uphill knees rather than hovering a foot. A leg is never folded under `FOLD` (0.55) of its posed hip-foot length -- past that the foot goes into the hill, which reads better than a knee folded flat, and a stag facing straight up or down a 20-degree slope on its near-straight front legs reaches it, its front hooves 5-9 cm into the turf and its front knees at 50-60 degrees -- nor stretched past `REACH` (0.995) of straight. Everything eases: a plant and an unplant ramp with the clip crossfade, a re-plant slides over `SETTLE_S` (0.12 s). What the solver writes it undoes before the mixer next runs, because the mixer only rewrites what a clip tracks and a bend left on an untracked joint would compound frame on frame. A solve is ~1.4 µs a step for a stag and ~0.7 for a snowman, against a mixer step of 1.2-1.8, and only bodies standing still on a planted clip pay it. The crabs, frogs and spiders still tilt onto the ground's normal, which a body that small can afford. The preview and the exported copy of a card carry the same bytes through different textures. ### Stage 4: rig-check first, always

`POST /v3/animations/rig-check` costs nothing and returns `riggable` plus a recommended `rig_type`. It is the only way to learn that a mesh will not take a skeleton without paying 25 credits to find out. The bench offers it as its own non-orange button and writes Tripo's suggestion back into the rig-type selector.

`rigType: 'none'` is a real answer, not a gap. A butterfly wants two textured planes on a hinge, and Tripo cannot model one from a photograph of spread wings -- so the bench's "cut wing cards" step (`tools/creatures/wing-cards.mjs`, free, local) cuts the picked image out and lays it on two quads that meet along the body, one 128px RGBA cutout drawn double-sided with a hard alpha cut, and files the 4-triangle glb as an ordinary mesh candidate (`kind: 'wing-cards'`, no Tripo task, so the rig steps refuse it). The cut fits a quadratic grey to the frame's edge ring, so the prompt's vignette is not foreground; a grey pixel darker than that model with no strong pixel below it in its column is the floor shadow the generator draws despite the prompt, and is dropped. The seam sits at the cutout's centre of mass plus the bench's seam offset. A picked wing-cards glb is already the shipped shape, so `ship.mjs` copies it whole (a critter only: `CRITTERS`) and `check-creatures.mjs` measures the PNG inside it instead of a WebP beside it. In the world the hinge is the vertex shader: `src/v2/render/butterflies.js` draws every butterfly from one InstancedMesh of the four triangles and a per-instance `aWing` (phase, amplitude, rest angle) turns each wing about the seam, normal and all -- a fast wide flutter in flight, a slow narrow pulse with the wings raised at rest -- so the flap costs no CPU per butterfly. They roll per 16 m tile at one per 100 m2 below the snow line at 5--20 cm of wingspan, fly 0.5--3 m over the walk surface the way a real one does -- sharp turn impulses over a weave, flap bursts and short glides that surge and bound the body, a climb capped at 40 degrees so nothing rises straight up, a per-stroke bounce on the wing phase -- and land on trunks, boulders, fern crowns, stumps, logs or the ground (`Ferns.perchesInto`, `Deadwood.perchesInto`, the tree and rock anchors); `scripts/check-butterflies.mjs` gates all of it on a synthetic meadow. A frog is small enough that a hop is a whole-body transform.

A grasshopper is a Tripo mesh generated at the bench's lowest face target -- the roster asks for a 16:9 side-on frame and a prompt that thickens every leg and antenna, since at a couple of hundred triangles anything thin is what goes first -- shipped by `ship.mjs` as `meadow-grasshopper.glb` (281 triangles) with its colour map boxed to a 128 px WebP and its node turned by `faceTurnDeg` to face +X. `src/v2/render/grasshoppers.js` draws every one from ONE InstancedMesh of that geometry, a single draw call under a plain Lambert with no LOD ladder: the mesh's X extent is scaled to each body's length, antennae tips to tail. They roll per 8 m tile at one per 16 m2 on ground under 38 degrees and 20 m below the snow line, 8 cm long give or take a fifth, each tinted between an olive green and a rust brown through instanceColor; only the ones within 8 m of her head are stepped or drawn. Each sits on the walk surface for 1--6 s then hops 0.2--1.5 m in length and in height, bent home past a 4 m tether -- and the hop is deliberately not gravity's symmetric arc, which reads as a dash: a crouch winds it up, the launch speed bleeds away through the flight so the apex comes at 42% of it and the drop in is steeper than the take-off, and the body squashes and recovers on landing. After sunset (`NIGHT_DAY`, the butterflies' line) none hops -- a rest that runs out is re-rolled, so dawn does not launch the meadow at once. The ambience lists the shown ones (`bodies()`) and chirps the cricket clip from one within 8 m about once a minute each, by day as well as by night; at night these are the near crickets, real bodies under the unplaced far bed, so there is no cricket beside her where no grasshopper sits. `scripts/check-grasshoppers.mjs` gates the shipped asset, the scatter and the hops.

A firefly has no asset at all: at 7 mm it is a dark speck by day and a point of light by night, so `src/v2/render/fireflies.js` draws every one from ONE InstancedMesh of a single quad laid as a sprite in view space (each eye of a stereo pair faces it squarely), and the fragment shader is the whole animal -- a 7 mm body disc in a near-black warm brown, and a lime halo (`GLOW`, linear 0.55/1.0/0.2) that is a bright pinpoint at the body plus a faint skirt to the card's 0.35 m edge, written in one premultiplied draw so the halo adds over the scene and the body covers it. Nothing in the scene is lit by it: the skirt tints whatever is behind the card, which is enough to see a little by and is not a light. The layer exists only while the world's day scalar is under `NIGHT_DAY` (the sun a degree below the horizon) and the glow ramps to full by `DARK_DAY` (four degrees below), so dusk brings them out gradually and the tiles are dropped, not hidden, by day. Each 16 m tile within 30 m of her head rolls candidates from its seed at one per 40 m2 on ground 20 m below the snow line, and a candidate becomes a firefly only once a trunk stands within 6 m of it -- the trees land over frames, so every tile's leftovers are looked at again in turn. A firefly wanders 0.3--3 m over the walk surface at 0.25--0.7 m/s, turn impulses over a weave, tethered to 6 m of where it was rolled, never over water.

The flash timings are the beetles'. A *Photinus pyralis* male's flash lasts about half a second and comes every 5.5--6 s at 20--25 C; *Photuris* flashes are shorter, a tenth to a fifth of a second; *P. carolinus* fires a burst of five to eight and then stays dark 8--10 s. All of them rise faster than they decay, and the *pyralis* male rises through the air as he flashes, which is the "J" his species is known by. So a flash is `ON_S` 0.3--0.7 s and a dark spell `OFF_S` 6--18 s -- twice the beetle's, a calmer wood -- both re-rolled every cycle so no two fireflies share a rhythm; the glow rises over the first `RISE` (30%) of the flash and fades over the rest; a flashing firefly lifts by `FLASH_LIFT` and slows to half speed. `scripts/check-fireflies.mjs` gates the scatter, the night gate, the snow and water refusals, the late trees and 90 s of flight and flashing on a synthetic wood.

**The skeleton comes back sound and the NAMES on it come back wrong, and only the names matter.** Measured on the red fox with `scripts/probe-rig.mjs`, which prints each joint's name beside where that joint actually sits on the animal: the hierarchy is correct -- root, pelvis, spine, chest, neck, head, front legs off the chest, hind legs off the pelvis, tail off the root -- but the labels are shuffled. The fox's spine is called `0_Left_Limb_1`, its chest `Head_0`, its front-left shoulder `Spine_0`, and all four legs are unnamed `bone_9` through `bone_29`. Rigging the same mesh twice produces different labels, so this is a guess being re-rolled, not a convention.

**Retargeting matches by name, so wrong names are a paid no-op.** `preset:quadruped:walk` on that rig drives **7 of 36 bones**: the pelvis, the two bones it thinks are limbs (the spine and the chest), and the tail. Every leg is frozen at its rest rotation for the whole 2.6s clip. Worse, the two mis-named body bones are held **98 and 95 degrees off their rest pose** for the entire clip -- a constant offset, not a gait -- which folds the fox's front half down until both front paws are driven 7cm below the ground plane. What it looks like is an animal walking on its tail with its body dragged behind, which is what it is.

So **the presets are not usable for quadrupeds**, and buying more of them will not help: the failure is upstream of the clip. Renaming the bones locally cannot fix it either -- `createRetargetTask` posts a rig *task id*, so Tripo animates the skeleton it stored, not the file we hold, and our names never reach it.

The bench's **bone names** checkbox draws the same labels over the preview, because a skeleton helper renders every bone as an identical white stick and which bone is which is the whole question.

### Stage 5: clips are solved here, not bought

**This is the preferred way to make a creature move, and Blender is the fallback.** `tools/creatures/anim/` turns a spec written in animator's terms -- stride, duty factor, footfall phase, step height, body bob -- into per-joint rotation tracks on whatever skeleton Tripo happened to emit, and bakes one `anim-<clip>.glb` per spec. It is free, it takes under a second for the whole library, and it re-runs from a button on the bench (`build clip library`), so editing a spec and looking at the result is a loop with no vendor and no DCC in it. `_notes/blender-rig-and-animate.md` remains the route for a hand-authored one-off; a clip authored there exports to the same filename and the bench cannot tell the two apart.

**The rig map is what makes this rig-agnostic.** Stage 4 established that the names are noise, so `anim/rig-map.mjs` derives anatomy from joint POSITIONS alone -- four chains ending on the ground in two mirrored pairs are the legs, the highest free tip is the head, the chain off the back is the tail -- and every measurement is taken in a body frame derived per rig, because the fox is modelled 45.9 degrees off X and a world-axis assumption gets it wrong. The result is written to `rig-map.json` and **read back verbatim on every later build**, so a creature the heuristic mis-reads is a ten-second hand edit rather than a code change. It is derived from `rig-fixed.glb` when a rig edit exists, which is also what makes the fox's map carry readable names.

**Two chains ending on the ground is a biped, and gets the `human` reading.** The villagers were rigged with Tripo's humanoid preset and their names are as random as a fox's -- one farmer's arms hang off a joint called `Head_0`, and the chains are not even the same length from one to the next (22 to 28 joints, three- to five-joint legs, arms of four to seven), so nothing is retargetable by name and the same clip is solved per rig instead. A standing figure offers only one cue to which way it faces, since its spine is vertical and it is as wide as it is long: a last leg bone that runs along the ground is a **toe**, and the toes say forward, snapped to the nearest world axis because Tripo poses a humanoid square to one and the toes themselves splay by twenty degrees. Left is the leg on the positive lateral side. The arms are the two longest remaining chains, one per side, hung off a common chest joint, and each is annotated `shoulder` / `elbow` / `wrist` by arc length along the chain from where it first leaves the flank, so a clip can drive the joints apart. The failure mode is stated rather than guessed around: the fisherman and the herbalist came back from Tripo with ONE leg reaching the ground and the other a stub joint at hip height, and the map throws naming that -- a re-rig (25 credits) or a hand-written leg in `rig-map.json` is the way on. The woodcutter's right leg is three joints with no toe, which the map accepts; that leg is solved to its foot and is shorter than the left, which is why the woodcutter's walk and run carry stride tweaks.

**That escape hatch is load-bearing, and three creatures have now proved it.** On the fen dragon the heuristic reads `ground` as the lowest joint in the rig, which is the tail tip -- 36cm *below* the feet -- so the foot band excluded the feet and it found zero leg pairs. Patching the heuristic until it handles tails is worse than a file you can fix by hand, so the dragon's map is hand-written; `plan: "wyvern"` is a hand-written field too. The snow hare needed the hatch for an unrelated reason: Tripo gave its right hind leg three joints where the left has four, so no mirrored pair sits in the low-leaf band at all. Tripo's moor stag rig needed it for a third: the head's low-leaf search ran off the neck into one EAR of a mirrored pair, so a head turn cocked that ear and left the skull and the whole antler rack behind.

**And a fourth creature needed a skeleton rather than a map.** Tripo's `octopod` rig on the birch spider (2 x 25 credits) is 33 joints of which two legs have four or five joints, five are zero-length stubs, and an eight-joint "tail" is one more leg -- there is no reading of it that yields eight legs. `tools/creatures/rig-spider.mjs` builds the skeleton from `mesh.glb` instead: it cuts the mesh at a box around the body, takes each connected piece outside it as a leg (it insists on exactly eight), walks the leg by Dijkstra from where it meets the body to its furthest vertex, and puts hip, knee, ankle and foot at 0, 1/3, 2/3 and 1 of that arc length on a smoothed centreline -- three bones per leg, joints evenly spaced along the tube whatever shape the leg arches in. The body joints are stated in the tool, not found -- pedicel, thorax, head, a chelicera and fang per side, two abdomen segments -- because a spider's anatomy is not something a heuristic reads off 573 vertices. Skinning is nearest-bone within a segment (a leg's vertices see only its three bones, the body's only the body's), which is what stops leg IV, which lies along the abdomen's flank, from carrying the abdomen with it. It writes `rig-fixed.glb` and a `plan: "spider"` rig map together; **a rig-edit save on that creature would regenerate `rig-fixed.glb` from Tripo's rig and clobber it**, and re-running the tool is the way back.

**The hob weevil's skeleton is stated outright.** Tripo's hexapod rig on it was unusable, and its legs do not bend at even thirds: the femur rises to a knee peak, the tibia drops to the ground, the tarsus lies flat. `tools/creatures/rig-hob.mjs` states every joint, read by eye off orthographic renders, after turning the mesh 46.75° so its mirror plane is x = 0; it reuses the spider tool's loader, skinning and writer. Each leg and each foot is its own mesh island, so a vertex's leg is exact; the body island is split between thorax and head by a plane at the pronotum's front edge, because nearest-bone would hand the pronotum's top to the head bone. Its map is `plan: "insect"`, whose clips (tripod walk and run, idle, a rooting eat) live in `anim/clips/insect`.

**Skin weights, not joint count or name, decide which joint drives a part**, and that is what made both those calls without a re-rig. The hare's right paw's 72 vertices are bound to the ANKLE, so an inserted bone would not have moved them -- the $0.25 would have bought nothing. Both hind legs are therefore read as three-joint chains ending at that ankle, which matches the pair to within 2cm in reach, rest height and fold slack and leaves each paw riding rigid below it; symmetric rigidity reads as stylised, where an asymmetric fix would have read as broken. The same measurement settles a chain the detector got wrong: Tripo's stag rig's `Head_3` carries **41% of the whole mesh's skin weight** with its centroid high above the skull -- it *is* the antler rack -- so it and its child belong in the head chain, and the ear bones the search picked instead carry 4.6% each. Positions say what the hierarchy looks like; weight mass says what a joint is worth moving.

**A joint at ground level is a rig defect that poisons every spine pitch.** `bend()` spreads a rotation over a chain about each joint's own position, so a spine whose first joint sits at the world origin swings the whole animal about a pivot on the floor instead of arching the back over the hips. Tripo put its stag's `Root` exactly there. `rig-edit.json`'s `moves` fixes that without touching the rest pose: the joint's world transform moves, its inverse bind matrix is recomputed so the skin is bit-identical, and its children are compensated so they stay put -- **what changes is where the joint pivots when animated**, which is the entire point. Moving that `Root` to the midpoint of its hind hips took `dig`'s stance miss from 38.6mm to 0.1mm on its own. It also turns a spine pitch into a genuine back arch, which the shared `sit` and `dig` specs over-drive on a back that long, so both take `scale: { spine: 0.6 }`.

**Because `bend()` spreads a rotation uniformly, a long chain curls into a spiral, and a head pitch reaches down only up to a point and then starts tucking back.** Measure the chain tip's `fore` offset from the neck base, not its height: on the stag the muzzle sits 236mm ahead at 1.5 and 1.8 radians, 231 at 2.1, 222 at 2.4 -- past the peak it is descending by folding under the throat, which reads as chin-to-chest, not browsing. Height alone cannot tell those apart, and the browse pose's first draft looked right by height and wrong on the sheet. **The head is also a weak lowering lever and the spine a strong one**, by different amounts on every body: 1.8 radians of head bend drops the stag's muzzle 138mm and the fox's 115mm on an animal two thirds the size, because the fox's chain tips out at the skull on a short neck. So the `eat` clips put their depth in `spine.pitch` and the fox pays for browsing height with `scale: { spine: 2.5 }` where the stag needs only 1.4.

**The dragon also settled a question by measurement that no amount of tuning would have.** Its forelimbs total 0.677m against the 0.812m needed to reach the floor from the shoulder -- short by 13.5cm on both sides, dead straight. It is not a folded bind pose, and crouching cannot help, because the hind legs would have to fold past where the foot already sits above the hip. **No animation-layer trick turns that mesh into a walking quadruped**, which is why `wyvern` exists as a plan rather than as a set of quadruped specs with the front legs fudged.

**Feet are driven by position and the limbs by IK; everything else is forward kinematics on sinusoids phase-locked to the gait.** That split is the whole design. A leg posed by rotating its joints slides its foot along the ground, and foot slide is the loudest tell of bad quadruped animation. The IK is cyclic coordinate descent with each interior joint pinned to the bend axis `cross(dirIn, dirOut)` it already has in the rest pose, stored in the joint's own frame -- so no knee can invert and no pole vector is needed, which is the one control Blender's Auto IK also does not give you.

**CCD converges slowly for a pure change of length, which is most of what a gait asks for.** Each pass the hip spends the correction on re-aiming and only the residual reaches the hinges, and the shorter the chain the worse it is: the fox's four-joint leg is inside a tenth of a millimetre in forty passes where the fen dragon's three-joint one is still skating four. So `iterations` is a **ceiling, not a count** -- `solveLimb` exits as soon as the foot lands or a pass stops moving it, which makes a ceiling of 240 cheaper than the flat 40 it replaced while ending the skating. A target that is genuinely out of reach plateaus and exits on the second test, so an impossible spec costs nothing to discover.

**A human leg is solved to the ANKLE, with the toe a rigid child.** Solved to the toe, the ankle is the joint with slack and CCD folds it through the floor. The map's `toe` names the child, and it is where the leg meets the ground: `pivotOnToe` turns a gait's toe-off into an ankle target that rolls over a still toe, and the sink and slide checks read the toe where one is named. Two more things a bind-straight knee needs. A joint bent under 20 degrees at rest (`STRAIGHT`) has a crease axis that is noise, and on these rigs the knee sits as often behind the hip-ankle line as in front of it, so a leg map may carry `hingeAxis`, which the biped map writes as the body's lateral into every leg; such a knee takes the given axis, and one creased the wrong way has its rest bend clamped to zero, so it can only fold. And a hinge at its straight stop while the foot overshoots the target is a leg too long for where it is going, which CCD cannot see: foot and target sit nearly in line from the knee, so it asks for no turn or one the wrong way that the clamp discards, and four of the seven villagers stood 39mm through the floor in every clip with the knee never folding. Turning the foot cannot shorten anything, so that case folds by the law of cosines to the target's distance from the hip and lets the hip re-aim, and the pass that did it is exempt from the plateau exit because the foot swings off line until the hip catches up.

**When more passes stop helping, the leg is out of leg -- and that is a spec question, not a solver one.** Sweeping the dragon's run stride against passes separates the two cleanly: below stride 0.72 the residual is pure convergence and vanishes with more passes; above it, 40 passes and 360 give the identical 27mm, because the hind leg only reaches 0.16 past its rest length. `crouch` is the lever that moves the wall, since lowering the hip is what buys the stride room to land.

**Body lift is paid for out of leg slack, and `crouch` is what buys it.** Tripo binds a creature at near-full extension, so a spec that raises `bodyBob` without also crouching runs the legs out of reach and the miss comes out as stance slide. `check-anim.mjs` gates the coupling directly: the same spec at `bodyBob` 0.12 slides 16mm at `crouch` 0.05 and nothing at 0.16.

**Fold slack is the one number that predicts whether a shared gait will fit a body**: `sum of segment lengths - |foot - hip|`. The fox has 2.7--5.7% of its chain in slack and the hare 5.7--13%; Tripo's moor stag rig gave its front legs **0.7%** -- 2mm in a 307mm leg -- on a wheelbase nearly double the fox's. A stride scaled by wheelbase then asks short locked legs for a long step, and at the default `FOLD_LIMIT` of 1.9 rad a deeper crouch only drove the feet through the floor. **Crouch buys bend back only once bending is allowed.** `limits: { fold, straighten, hipLimit }` is a top-level spec key for exactly this; widening that stag's `fold` to 2.7 took its trot's swing miss from 56mm to 3mm, but its foreleg joints sat off the real elbow and carpus, so every step still bent the cannon. **A leg whose joints are in the wrong places cannot be tuned straight; re-rig it.** `rig-stag.mjs` states each joint off orthographic renders as `rig-hob.mjs` does: three bones per leg, all in one vertical plane so the hinge is a clean lateral axis, the hoof rigid below the cannon, and the skin split by distance to each leg's bones so belly, sheath and hooked tail tip stay on the body. That stag walks at default limits. **A leg map may carry `give: { <joint>: 0..1 }`**, which scales every CCD turn at that joint: the stag's carpus takes 0.15, so lowering the chest to graze bends the elbow, where at 1 the foreleg Z-buckled at the carpus. A fold-down needs the opposite, so a pose spec's `limits: { give: false }` turns every joint freely: at 0.15 the stag's `lie` sent the elbow up past the shoulder. **And `crouch` sets standing height, so it has to be held near-constant across a creature's whole gait family**, idle and alert included -- the shared specs spread it 0.02--0.06, which on the stag is a 26mm pop between clips; its tweaks hold it at 0.04.

Clips are **in place** -- the ground moves under a stationary animal, which is what the engine wants and what the bench previews. The forward speed a gait implies is `stride / (duty * duration)`, and `diagnose()` uses it to check that a planted foot is genuinely still in the ground's frame. Every clip is one animation in one file, because the bench plays `gltf.animations[0]`.

**Specs are grouped by BODY PLAN, because a fox and a two-legged dragon do not share a walk.** They live in `anim/clips/<plan>/`, and a rig map's `plan` field selects the library -- absent means `quadruped`, which is what every Tripo rig is. Each spec carries a `note` saying what makes it that gait, opening with which animals it suits where not every body in the plan shares it.

Every standing clip starts and ends at the idle stance, and the four `talk-*` clips also keep the head within a few degrees of straight ahead, so any of them can follow any other on two facing NPCs and a conversation is a shuffle of the four. `sit` goes standing to seated and back; `idle-sit`, `eat` and `lie` start and end at its hold numbers restated verbatim, and `sleep` at `lie`'s, so the seated and lying families cut together the same way. The three seated clips declare `chainsTo` in a ring (`eat` and `lie` to `idle-sit`, `idle-sit` to `lie`), so the gate holds them to one shared hold; `sit`'s own hold and `lie`'s are mid-clip, which `chainsTo` cannot reach, so those two restatements are still kept by hand. **A human's `wheelbase` is its hip height above the ground**, the natural stride and reach scale on two legs, and it is also nearly the whole leg: the ankle sits 3 to 6cm up and a straight leg reaches about 0.86 of it, so a stride of 0.9 was out of reach on the hunter and the walk sits at 0.8; the woodcutter's short toe-less right leg needs 0.7 and 0.85. The pose handles a human clip leans on are `root` rotation, which pivots the whole figure about the mean hip so a lean-back or a lie-down keeps the hips where they are and the feet are re-solved under them, `crouch`, which every pose clip carries at the idle value, and the **jointed arms**: a rig map's arm annotated with `shoulder`, `elbow` and `wrist` is driven by `anim/arm.mjs` through `arms.left` / `arms.right` / `arms.both` with `shrug`, `raise`, `spread`, `twist`, `elbow`, `wristPitch`, `wristSpread` and `curl`, all radians, all deltas from the rest pose, because Tripo binds an elbow forty degrees bent and an upper arm thirty out from the flank and a spec cannot know that. Each axis is carried by the joint it turns, so raising the arm and then bending the elbow brings the hand to the shoulder rather than to a fixed point in the room. `shrug` turns the clavicle joints before the shoulder about the body's forward axis and counter-turns the shoulder by the same angle, so the shoulder lifts while the arm keeps hanging; every Tripo humanoid so far has one clavicle joint, and an arm with none shrugs nothing. The signs were established by measurement on the blacksmith: `raise` pi/2 is straight ahead, `spread` pi/2 straight out, positive `elbow` folds the hand toward the shoulder, positive `twist` turns the wrist inward, and an elbow folded without twist swings the forearm in the sagittal plane, which is how a hand meant for the chest ends up behind the shoulder: bringing it to the chest or the mouth takes a twist of 1.3 to 2.3 so the forearm folds across the body. A gait drives the same arms with `armSwing` (against the leg on that side), `armElbow` and `elbowSwing`.

The poses are `kind: "pose"` -- keyframed body targets interpolated and then IK'd, rather than a cycle -- and their hold is a **flat pair of identical keys** so a game can cut one clip into down / rest / up at the hold.

**A dig cannot be a gait even though it cycles.** A gait moves every planted foot at one ground speed; a digging animal rakes its forepaws backwards while its hind feet stand still. So `dig` is a pose clip, and it needs one fact the geometry cannot supply: a raking paw sits at its own rest height, so it *is* planted by measurement, and scoring it as stance reports the intended stroke as a skid. `unweighted: [legId, ...]` says which feet work at ground level without carrying the animal. The alternative -- raising `samples` until the per-frame number fell under the gate -- would have been gaming the metric rather than stating the fact.

**A fold-down measures from where the leg hangs, not where the mesh stood.** Tripo's stag was modelled mid-stride, so forefeet offset from their rest positions folded one leg neatly and drove the other's carpus 6cm underground. A leg handle `under: 1` slides the base those offsets are measured from to beneath the leg's top joint. `ground: 1` lowers it to the rig's lowest joint, a no-op on a hoof and the whole point on a hare, whose hind foot joint is an ankle 16cm up. A grounded foot reports that lowered height as its `floor`, and `diagnose()` reads sink and float from it, so a foot put down on purpose is not scored as sunk. The hare's hind paw rides rigid below that ankle, so in `lie` it goes into the ground under the haunch. Pitching it flat would fix that, but the same `pitch` stands the stag's hind hooves on end and flips the fox's paws.

**A clip that holds a state for an unpredictable length of time has to be three clips, not one.** A stag browses for as long as the world says, so `eat` is `eat-down`, `eat-loop` and `eat-up`: the world plays the descent once, the loop any number of times, then the rise. A single down-hold-up clip cannot do that, because the hold is whatever length the spec baked in. The cost is a new kind of clip -- **a one-way transition, which by definition does not return to its first pose** -- and the gate asserted `loopGap < 1e-3` on every clip, an invariant that was true only because every clip so far happened to be a round trip. So a spec may declare `loops: false`, which exempts it from that one assert and nothing else. In exchange it owes a different promise, and `chainsTo: "<clip>"` is it: the clip's last key pose must equal the named clip's first, compared with zero handles dropped so an omitted handle and an explicit `0` are the same thing, since `sample` reads both as zero. **The seam is the one defect a contact sheet cannot show** -- each clip looks right on its own and the pop exists only between two files -- so it has to be a number. Tweaks are checked the same way: two chained clips tuned differently on one body agree in the shared spec and still pop on that animal, so a creature's `clipTweaks` for a chained pair must match.

**A shared spec carries across bodies only mostly, and `scale` is where the rest goes.** Foot offsets go by `wheelbase`, which is right for a gait and too far for a fold-down on a long body: the hare's wheelbase is 1.9x the fox's on shorter legs, so the fox's trot over-reaches and its sit stretches the forepaws past where hare legs go. Tail angles fail the other way -- the fox's sit sweeps its tail 2 radians, which the hare's short thick one turns inside out at the base, and the shared `tailPitch` of 0.9--1.25 stands a deer's short tail straight up so the stag reads as permanently alarmed in every clip until it is cut to about a third. **The tail is in no IK chain, so nothing in `diagnose()` moves when its carriage is wrong**; that one is the contact sheet's to catch. Retuning the shared spec would drag every other creature along, so the tuning belongs to the animal: a rig map may carry `clipTweaks: { <clip>: { <key>: value } }`, laid over the top level of the spec, and `scale: { <group>: <number> }` dials one group of handles for one body. Shallow on purpose -- **a tweak that had to reach inside a pose's keyframes is a spec of its own, not a tweak** -- and shallow means *replaced* one level down as well, so a `limits` tweak drops whatever the spec's own `limits` held: a stag `lie` tweak restating only `hipLimit` dropped the spec's `fold: 2.3` to the 1.9 default and left the forefeet 16mm short. Both are resolved by name at solve time, so a misspelling is silent; `check-anim.mjs` gates the names in the spec and in every rig map's tweaks.

**The pitch signs are counter-intuitive and were established by measurement, not by looking at renders** -- inferring them from a contact sheet got them backwards twice. Posing each chain directly and reading world positions off the fox: positive `spine.pitch` puts the front end DOWN, positive `head.pitch` puts the nose DOWN, and positive `tail.pitch` puts the tail UP. One sign convention, following the chain rather than the body -- a positive pitch about the lateral axis drops a forward-pointing chain and lifts a backward-pointing one, which `check-anim.mjs` states as a pair of checks.

**Wings and arms are driven as MIRRORED PAIRS, one amplitude for both.** An animator thinks "beat the wings", not "roll the left one +0.6 and the right one -0.6", so the map's `side` carries the sign and a spec never has to know which way round the rig is built. The axis decides whether that is a sign flip or a phase offset: a roll about `fwd` must be negated across the pair for both wings to go down, while a fore-aft swing about `lat` is antiphase. `bobPhase` exists for the same reason -- a gait's bob is phase-locked to footfall, but a flying animal rises through the downstroke, a quarter cycle off the default -- and `spineFlexPhase` is the same knob for the back, because where in the cycle a bound's spine hollows out is its footfall order and not the solver's: on the hare's bound the shoulders lift with the push, and a flex peaking as the fores land put them out of reach of the ground by 30mm until the peak was moved to the gather. One amplitude spread along the whole chain is right for a forelimb tucked under a wyvern and useless for a human, whose wave is a raised upper arm, a bent elbow and a hand that flaps; that is what the jointed handles above are for, and an arm map with a `shoulder` annotation takes them instead.

**Judging a clip has two instruments and they answer different questions.** `anim/sheet.py` renders a contact sheet through Blender, aimed down the creature's own lateral axis with a ground plane drawn at the rig's ground height, because whether a foot is planted, sliding or floating is not a thing the eye can judge without a contact reference; `--view side|right|front|quarter` moves the camera, and a human's right-arm gestures are read from `right`, since the default `side` is the figure's left flank and hides the arm doing the work. `diagnose()` gives the numbers the eye cannot: `stanceSlide` is the one to read. **Stance and swing residuals are different facts** -- a stance miss is skating and a bug, a swing miss means the leg ran out of leg. On the fox the whole library solves in 0.5s at 0.1--0.2mm stance slide for the gaits; `sit` and `lie` sit near 10mm because the hind paws genuinely scoot as the animal folds, which is why the gate holds poses to 15mm and gaits to 3mm. **Plantedness is judged against each leg's OWN rest foot, never against one ground plane.** `ground` is the lowest joint in the whole rig and need not be a foot -- the hare's hind pair are ankles 16cm up, the dragon's tail tip is 36cm below its toes -- so a single plane reads those legs as permanently airborne, and an airborne leg is exempt from the slide check. `diagnose()` had this right and `poseClip` did not, which hid most of every pose clip's feet from the gate: correcting it is what exposed the dragon's sit and lie scooting 25mm, three times the fox's, because a relative reach on a much larger body is that many more millimetres. **A contact sheet cannot judge height**, only contact: `sheet.py` frames its camera on the animated mesh bounds and draws the ground line relative to that centre, so a constant lift is invisible by construction -- doubling an airborne clip's altitude renders the identical image. And `diagnose()` measures penetration on FEET only, so a tail dragged through the floor passes the gate and has to be caught by eye.

`scripts/check-anim.mjs` is network-free and runs against a **synthetic skeleton it writes itself**, since the work dir is gitignored -- deliberately harder than any real rig (a three-joint front leg, the fewest `limbSetup` accepts, is the worst case for convergence). It gates five failure classes: a planted foot drifting, a hinge inverting, a track coming out short, the root translation landing in the wrong space, and a clip ceasing to loop. It also runs `buildRigMap` over a biped fixture and checks the reading it gives -- plan `human`, forward from the toes, ankle and toe per leg with the lateral as hinge axis, the arms found and annotated, nothing left unclaimed -- and that the same fixture with one leg cut to a stub throws rather than returning a one-legged map. It then re-solves every shipped spec on its plan's fixture, which is the rig-agnostic claim stated as a test, and finally runs the real library for any creature that has a rig on disk, against that creature's own plan.

**One fixture skeleton carries the quadruped, wyvern and spider plans**, because those plans are readings of a rig rather than different rigs: the wyvern map stands the same skeleton on its hind pair, demotes the front pair to arms, and drives the wing joints that the quadruped map leaves inert; the spider map adds two mid pairs of legs the other two leave inert and drives the wing chains as chelicerae. The biped gets its own skeleton, because toes and hanging arms are not a reading of a quadruped's legs. Every plan directory needs an entry in `FIXTURES` or its specs would go unchecked, so the gate fails on a missing one rather than quietly skipping it.

## The spend model

The project's standing rule is that external API dollars are a separate budget from tokens and never get spent without a human deciding. That rule is implemented, not just documented:

- **Nothing fires on its own.** No retry loop, no auto-advance between stages, no batch. Each stage is one explicit click.
- **The price is on the button face**, computed by `estimateCredits` -- pure arithmetic, no network -- before the click. It lives beside the request builders in `tripo.mjs` so a cost-changing parameter cannot be added without the estimate landing in the same diff, and the gate pins the resulting table against Tripo's published prices.
- **Orange means it charges a card.** `button.spend` in `gen-creature.html`; `button.local` is the free half of the bench, which is now where the clips come from. `rig-check` is not orange.
- **The ledger sums server-reported costs only**, never client estimates -- what the page shows is what was actually billed.
- **`waitForTask` has a hard timeout and no retry.** A stuck task is something to look at, not to silently resubmit; a retry loop here spends money per iteration.

## State on disk survives a restart

Everything lands under `tools/creatures/work/<id>/` (gitignored -- these are working sources; the bake step is what writes `public/`):

```
candidates/<n>.png       every generated candidate image
source.png               the picked one -- the single image every Tripo step reads
meshes/<n>.glb|.fbx      every generated mesh, in the container Tripo sent
meshes/<n>-preview.png   Tripo's own render of it
meshes/<n>-lod<k>.glb    LOD tiers, decimated locally from that mesh
mesh.glb|.fbx            a copy of the picked mesh -- what the bench reads
rig.glb                  skeleton bound to the mesh
rig-edit.json            bone renames, reparents, deletions and joint moves -> rig-fixed.glb
rig-fixed.glb            the skeleton the builds prefer over rig.glb: rig-edit's output, or the spider's authored one
rig-map.json             what each joint IS, derived from geometry -- hand-editable
anim-<clip>.glb          one file per clip, solved locally or retargeted by Tripo
sheets/<clip>.png        contact sheets, for judging a gait by eye
state.json               task ids, credits, picks
```

**The container is read off the bytes, never assumed.** `quad: true` makes Tripo deliver FBX rather than glTF, because glTF has no quads -- and only on models that accept the flag, so a P1 run (where it is stripped) and an H3 run with identical parameters come back in different containers. `containerOf()` in `workspace.mjs` sniffs the magic before naming the file, so a candidate is `1.fbx` when that is what arrived; writing it blind to `.glb` surfaced much later, in GLTFLoader, as `Unexpected token 'K'` on the FBX header. The bench picks its loader from the extension. Rigging is unaffected either way: it is driven by the task id, and Tripo re-derives from its own copy.

**Nothing paid for is ever overwritten.** Images and meshes are both numbered candidates; the bench lists them and a pick copies one into the fixed name the next stage reads. Images are cheap enough to want several of, so the bench lets generations queue -- the button goes dead for a second and then takes another click, while meshes stay strictly one at a time at 50 credits apiece. Concurrent image writes mean the slot number cannot come from `state.candidates.length`: `saveCandidate` *claims* it on disk with an exclusive write, so two requests that pick the same number cannot both win it. An image can be deleted from the gallery (the only destructive control on the page, and the only one that asks first); `source.png` is a copy rather than a link, so deleting the picked candidate leaves the Tripo input intact and only clears the pick. `state.tasks[step]` holds the *current* handle only and is overwritten by the next run of that step, so it is not a record -- `state.taskLog` is, appending every task id the account was ever charged for whether or not a pick still points at it.

**A Tripo task id is the only handle on work already paid for.** `charge()` in `workspace.mjs` writes it the moment the task is created, *before* the wait, so a dev-server restart mid-generation loses the poll and not the purchase. For the same reason every output is downloaded to disk in the request that observed success: Tripo's result URLs are CDN links that expire, and there is no task-history endpoint (see below) -- a lost id is 50 credits that cannot be re-fetched.

Picking a mesh moves `tasks.mesh` with it. Rigging is driven by the task id rather than by the file, so a pick that left it behind would rig a different mesh than the one on screen.

The bench's stage buttons gate on `/__creature-assets`, which reads that directory, so a reload mid-pipeline resumes where it stopped rather than restarting.

The bench's library overlay lists every creature the roster seeds *and* every directory under `work/`, with its prompt, its thumbnail, what stages exist for it and what it has cost so far. **The prompt is editable and saves into the creature's own `state.json`, not into the roster file.** That is what lets a creature be invented in the page and survive a reload without an edit to `creature-roster.mjs`; the roster stays a seed list, and promoting a settled creature into it is a separate, deliberate act.

**Nothing here reloads on save -- not the page, not the Node half.** Vite's HMR is off (see `server.hmr` in `vite.config.js`), and its restart-on-config-change rides the same disabled path and is deliberately not re-hung: a restart while a Tripo poll is open drops the connection on a job the vendor bills for regardless, and an agent saving `workspace.mjs` is enough to trigger one. So a change to any server-side file above needs a manual `npm run dev` restart, taken between generations rather than during one.

Orchestration lives in `workspace.mjs` rather than in the Vite plugin so a batch script can drive the same pipeline later without a browser. `creatureGen()` is a thin wrapper: it validates the creature id (`/^[a-z0-9-]+$/`) and returns JSON for every outcome including errors.

**The id validator is a security boundary, not tidiness.** It arrives from a query string and is concatenated into a filesystem path, and the dev server binds to the LAN (`server.host`). `../` in that string is an arbitrary file write. The gate tests it against traversal directly.

`TRIPO_API_KEY` and `OPENROUTER_API_KEY` live in `.env` (gitignored) and are read only by dev-server middleware. Neither ever reaches the browser.

## Baked puppets

`makePuppet` hands every creature layer a `BakedPuppet` by default and a skinned `Puppet` on request. Both answer the same API (`play`, `step`, `show`, `bones`, `meshes`, `feet`, `release`), so a layer only branches where it built a solver: dragon tail lag and the wild strider's head turn get `solverStub()` when `p.baked`. Motion that needs no live input belongs in a clip instead: the strider's shake and paddle are clips made at load (`strider-clips.js`) and bake like any other. The player's avatar stays skinned; it is posed from the headset.

**Layout.** Per skeleton (one `vatFor` per `asset.skeleton`), every clip is sampled at 30 fps (lowered until the rows fit 4096), n+1 rows per clip, and each row holds `bone.matrixWorld x boneInverse` as three RGBA float texels per bone. The vertex shader fetches two rows and blends them per instance (`aVat` = row0, row1, blend); the CPU keeps the same matrices so `bones[i].matrixWorld` still answers grip points and seat heights. One `InstancedMesh` draws one look (the plain material, twinned with the VAT splice) x one tier geometry x settled-or-fading; instance colour is `plain.color x puppet.tint`. `bakedRoot` flushes every shown puppet inside the scene's matrix pass, skipping any whose group is hidden or out of the scene, and any whose pose sphere (`poseSphere`, the skinned body's own) misses the view camera's frustum (`cullBakedTo`). The flush runs before three poses the headset's eyes, so the test is against the last frame's union of both, the sphere grown by 0.5 m plus 0.15 rad of its distance for a frame's turn and travel. The culled bodies are simply never packed into the batch, which costs one sphere test each on a loop that repacks every body anyway.

**Swap.** `?puppets=skinned` or `?puppets=baked` at load (remembered in localStorage `v2.puppets`), or the menu's "creature bodies" row, which rebuilds the room where she stands (ignored indoors). The gates that read a skinned Puppet's internals pin `setPuppetMode('skinned')`; `node tmp/skinned-gate.mjs scripts/check-x.mjs` runs any other gate skinned.

**Given up.** Foot IK (planted feet do not conform to a slope), clip crossfades (a `play` cuts), and the solvers above. In exchange each body wears its own colour for free on the instance colour: baked hobs, leafkin and dragons roll any light hue (`rollTint`), wildlife and striders one along their kind's natural coats (`tintRange`), each seeded by its key (`tintFor`), and all share a single plain material. A tier drawn short (a wild strider's bare body, its full one's buffers short of the tack) keeps its draw range in its batch.

## Adding a second vendor

The seam is `tools/creatures/tripo.mjs`. It exports a small surface -- `uploadImage`, `createMeshTask`, `createRigTask`, `createRetargetTask`, `waitForTask`, `estimateCredits` -- and `workspace.mjs` is the only caller. A Meshy client implementing the same surface would slot in behind a model selector, at the cost of losing non-biped rigging for creatures generated through it. Nothing else in the tree imports the vendor client.

## What the live API actually answers

Tripo's published docs are inconsistent about the base URL, showing both `api.tripo3d.ai/v2/openapi/...` and `openapi.tripo3d.ai/v3`, and the developer portal is a JS shell that a fetch tool cannot read. The paths below were settled by probing the live API instead. Every probe was free: upload costs nothing, and the existence checks POSTed an empty body, which fails argument validation before a chargeable task is created.

| what | v3 path | notes |
| --- | --- | --- |
| upload | `POST /v3/files` | returns `data.file_token`, prefixed `file_` |
| mesh | `POST /v3/generation/image-to-model` | |
| rig check | `POST /v3/animations/rig-check` | |
| rig | `POST /v3/animations/rig` | |
| retarget | `POST /v3/animations/retarget` | |
| task poll | `GET /v3/tasks/{id}` | |
| balance | `GET /v3/account/balance` | free; `{ balance, frozen }` in credits |

**The image goes in a nested `file` object** -- `{ file: { type: 'png', file_token } }`. A top-level `file_token` is not rejected, it is ignored, and the request fails as "file is required for image_to_model", which reads like the upload broke rather than like a wrong field name. The animation endpoints are the opposite shape: `input` is a bare task-id string, and nesting it there fails instead. No outer `type` field is needed anywhere; the path already names the operation.

**v3 renamed both the upload route and its field.** v2 was `POST /v2/openapi/upload` returning `image_token`; anything written against v2 will 404 with code 4001 ("No endpoint found") and no HTML page to make the cause obvious. `/v3/upload`, `/v3/upload/sts`, `/v3/file/upload`, `/v3/files/upload`, `/v3/uploads`, `/v3/balance`, `/v3/user/balance` and bare `POST /v3/generation` all do not exist.

Server-allowed mesh models are `P1-20260311, P2-20260801, v2.5-20250123, v3.0-20250812, v3.1-20260211`; rig models are `v1.0-20240301, v2.5-20260210`. **`P2-20260801` exists and this pipeline does not use it** -- P1 is still the default for the native low-poly reason above, and P2's pricing and topology are unmeasured.

The wallet is the other thing a first run discovers. The bench reads `/v3/account/balance` at startup and says so in the panel, because an empty wallet and a broken pipeline are indistinguishable from inside a spend button.
